# TASK-EAR-202 — Expose Weekly completion-bonus claim through API Gateway

## Type

feature

## Workstream

backend

## Priority

medium

## Created

2026-08-03

## Context

Mobile needs this public call:

```http
POST /api/v1/missions/claim-weekly-completion-bonus
Content-Type: application/json

{"user_id":"<user-id>"}
```

The Weekly claim route, handler, eligibility, claim ledger, deterministic
per-user/per-week wallet idempotency, and wallet credit already exist in
`Games-Labs-Missions` on `staging` under TASK-EAR-123. The public gateway
returns 404 because `shared-lib` does not define the Weekly RPC/HTTP annotation
and Missions has no generated gRPC bridge method.

`api-gateway` already registers `missionspb.RegisterMissionsServiceHandlerFromEndpoint`.
After it adopts the generated shared-lib contract, it needs no second manual
route registration.

## Goal

Expose the existing Weekly completion-bonus claim behavior through
`api-test-gateway` without changing eligibility, reward resolution, claim
ledger, wallet idempotency, persistence, or Daily behavior.

## Branch and authorization boundaries

- `shared-lib`: branch from `main`.
- `Games-Labs-Missions`: branch from `staging`; this claim flow is absent from
  `main` at task creation.
- `api-gateway`: branch from `staging` for the test-environment rollout.
- Use clean repo-local branches or isolated worktrees; preserve unrelated
  shared-workspace changes.
- Do not commit, push, open PRs, merge, deploy, or execute a live
  reward-crediting mutation without explicit operator authorization.

## Scope and gates

### Gate 1 — shared-lib public contract

1. Add `ClaimWeeklyCompletionBonus(google.protobuf.Struct) returns
   (google.protobuf.Struct)` to `MissionsService`.
2. Add `google.api.http` binding:

   ```proto
   post: "/api/v1/missions/claim-weekly-completion-bonus"
   body: "*"
   ```

3. Mirror `ClaimDailyCompletionBonus`; do not invent a typed DTO or new
   dependency.
4. Run `make buf`; never hand-edit generated protobuf, gRPC, grpc-gateway, or
   Swagger files.
5. Verify the generated RPC and HTTP path, then stop and hand the exact commit
   to the operator for publication. Mark the task blocked on the published
   shared-lib pseudo-version. Do not use a local `replace` directive for
   consumers.

Affected files:

- `shared-lib/proto/missionspb/missions.proto`
- Generated by `make buf`:
  - `shared-lib/proto/missionspb/missions.pb.go`
  - `shared-lib/proto/missionspb/missions_grpc.pb.go`
  - `shared-lib/proto/missionspb/missions.pb.gw.go`
  - `shared-lib/proto/missionspb/missions.swagger.json`
  - `shared-lib/proto/missionspb/swagger.pb.go`

### Gate 2 — Missions gRPC bridge, after publication

1. Bump `github.com/SparqLab/shared-lib` to the operator-provided published
   version; update `go.mod` and `go.sum` together and run `go mod tidy`.
2. Add `Server.ClaimWeeklyCompletionBonus` in
   `internal/handlers/mission/grpc/server.go`. It must bridge to the existing
   `s.HTTP.Weekly.ClaimWeeklyCompletionBonus` handler with `POST`, the same
   public path, and `httpx.StructToJSONBody(in)`.
3. Extend the existing `weekly_bridge_test.go`; do not create a duplicate
   fixture.
4. Do not change the existing Weekly HTTP handler, `WeeklyService`, repository,
   reward logic, or idempotency behavior.

Affected files:

- `Games-Labs-Missions/internal/handlers/mission/grpc/server.go`
- `Games-Labs-Missions/internal/handlers/mission/grpc/weekly_bridge_test.go`
- `Games-Labs-Missions/go.mod`
- `Games-Labs-Missions/go.sum`

### Gate 3 — api-gateway generated route, after publication

1. Bump to the identical published shared-lib version and run `go mod tidy`.
2. Do not modify `gateway/grpc.go`: the existing Missions registration picks up
   the generated route.
3. Add a focused `gateway/missions_routes_test.go`, using the existing
   `adminwallet_routes_test.go` pattern, to prove the path resolves through a
   grpc-gateway mux rather than 404.
4. Add the Weekly request to the API Gateway Postman collection, including
   request body, successful claim, repeat-claim, and incomplete eligibility
   behavior.

Affected files:

- `api-gateway/go.mod`
- `api-gateway/go.sum`
- `api-gateway/gateway/missions_routes_test.go` (new)
- `api-gateway/docs/Games-Labs-APIs.postman_collection.json`

### Gate 4 — staging rollout and Mobile handoff

1. Deploy Missions before API Gateway. A new gateway against an old Missions
   server would match the route but return gRPC `Unimplemented`.
2. Smoke the endpoint through `api-test-gateway` with an authorized staging
   identity.
3. Only with separate operator authorization, record wallet before the first
   claim, after it, and after a repeated claim.
4. Mobile enables the action only after gateway smoke succeeds.

## Acceptance criteria

1. Generated grpc-gateway code registers
   `POST /api/v1/missions/claim-weekly-completion-bonus` with a
   `google.protobuf.Struct` body passthrough.
2. Missions implements the generated RPC by bridging to its existing Weekly
   handler; it introduces no new business logic or duplicate DTO.
3. A Gateway mux test proves the Weekly POST route resolves rather than 404.
4. The request remains `{"user_id":"<id>"}`; no client idempotency key is
   required or forwarded to Wallet.
5. Existing semantics remain unchanged: successful claim is HTTP 200 with
   `status: credited`; repeat is HTTP 200 with `status: already_claimed`; an
   incomplete Week remains a business error.
6. Daily completion-bonus behavior and all existing Missions routes remain
   unchanged.
7. No migration, local `replace`, new dependency, duplicate gateway
   registration, or reward/service/repository change is added.
8. Both consumer repos update `go.mod` and `go.sum` together and build with
   `GOWORK=off go build -mod=readonly ./...`.
9. Staging deploys Missions before API Gateway and authenticated gateway smoke
   passes before Mobile enables the button.
10. If authorized, duplicate QA proves exactly one wallet credit with
    before/after balances; otherwise that live mutation remains a release gate.

## Bound the actual boot session: proposed follow-up, not implemented

The current `cmd/main.go` passes a signal-only context to `migrations.Run`; `migrations/run.go` opens `database/sql` from the application pgx pool. Repository 3 s query timeouts are initialized later. Goose v3.24.3 uses separate SQL executions in one transaction, and its session advisory locker defaults to retrying for up to 300 s. There is currently **no proven overall migration deadline**; a prebuild shell's `SET` does not affect it, and `statement_timeout` by itself is per statement, not a total migration limit.

Recommended design for an independently reviewed follow-up (no changes in this preflight): use a **dedicated migration pool** whose pgx `ConnConfig.RuntimeParams` are set before connecting, for example `lock_timeout=2s`, `statement_timeout=20s`, `transaction_timeout=30s`; give the entire `migrations.Run` call a `context.WithTimeout` of 60 s, including pool acquisition and Goose advisory-lock retries, and close the dedicated pool before starting normal application traffic. These are proposed values requiring operator/reviewer agreement and real staging measurements; PostgreSQL 18 `transaction_timeout` terminates the session, so verify pool disposal, rollback and fatal startup behavior. Prove the *actual migration backend* sees these values and that a held lock, slow statement, long transaction and held Goose advisory lock each cause bounded failure and transaction rollback, with no 070 version receipt; test successful retry and normal startup on staging. Measure the whole boot path, including initialization before the migration deadline, cancellation/cleanup and listener/health readiness against the actual ECS health budget. A context deadline is not proof of a strict wall-clock bound until cancellation and cleanup are measured. This requires a separate code/runtime change and release review, not a modification to migration 070.

Other option for review: temporary `ALTER ROLE ... IN DATABASE ... SET` defaults for new sessions plus PostgreSQL 18 `transaction_timeout`. It affects **all new connections** of the shared role/database, not just migration; it does not by itself bound Goose's advisory retry before BEGIN. Verify role, existing defaults, pool reuse, side effects and restoration, and obtain the required approval before any such configuration change. Do not apply it during this preflight. References: [PostgreSQL 18 timeout semantics](https://www.postgresql.org/docs/18/runtime-config-client.html), [role settings apply at login](https://www.postgresql.org/docs/18/sql-alterrole.html).

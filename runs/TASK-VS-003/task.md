# TASK-VS-003 — VerifySlip 600/min capacity measurement

## Context

Live load reports on 2026-09-24 mixed duplicate slips, validation failures, and
bank timeouts. The k6 script can reuse payloads across virtual users and counts
HTTP 409 as success without tracking HTTP 202 queue completion. Production
slip-system configuration is being changed separately by the team.

## Goal

Make a repeatable load test that can prove the number of distinct live slips
completed per minute and add focused queue observability for diagnosing
backpressure, without changing the public verification contract.

## Scope

- `jaview/60 Loadtest`: assign each iteration a unique payload from the input
  pool, stop when the pool is insufficient, report response classes separately,
  and follow accepted queue jobs to a terminal result.
- `slip-api`: expose focused verification queue metrics needed to distinguish
  admission, backlog, completion, and busy requeue behavior.
- Remove the hardcoded API-token fallback from the tracked smoke script.
- Start code branches from `main` and target PRs at `main`.

## Out of scope

- Do not run a new live-bank load test without a reviewed distinct-slip fixture
  and bank-approved test window. Do not merge, deploy, or adjust bank timeout,
  replica count, or shared attempt budget from this task.
- Defer changes to queue persistence or retry scheduling until metrics show
  worker occupancy is a limiting factor.

## Acceptance Criteria

1. The k6 script cannot silently reuse a payload in a single run; it counts
   200, 202, 409, 422, 429, 500, and 504 separately and reports terminal
   queue results for 202 responses.
2. The run summary identifies attempted unique payloads, immediate responses,
   queued completions, and incomplete jobs without treating duplicates as
   successful bank verification.
3. Queue metrics expose pending/processing count, oldest pending age, completed
   outcomes, and busy requeues, with bounded database work.
4. Focused tests, Go repository tests/build, k6 syntax or smoke validation,
   and task YAML validation pass. No live-bank traffic is generated by tests.

## Wave 2 — verify quota lock contention (added 2026-09-24)

Evidence: in the 14:16 and 14:36 live 600/min runs, the 504s stop at 3.0s
(slip-api `queryTimeout`) and the 500s ("verification failed") return at ~1s.
slip-system logs are clean in both windows. slip-api logs `request_logs` batch
deadlocks (40P01). RDS `upslip-postgres-prod` CPU stays ≤22% while connections
climb from 86 to 192, which points to lock waits rather than resource
saturation.

Cause: `SaveWithQuota` → `consumeQuotaInTx` → `processExpiredForBranchChannelTx`
→ `lockBranch` (`FOR UPDATE OF b, m`) + `lockActiveUser` (`FOR UPDATE`) on every
verification. All verifies for a branch serialize on these rows. `FOR UPDATE`
also conflicts with the FK `KEY SHARE` locks taken by `request_logs`,
`verifications`, and `quota_history` inserts.

Scope:
- `lockBranch` / `lockActiveUser`: `FOR NO KEY UPDATE`; key columns are never
  updated there.
- `SaveWithQuota`: atomic quota fast path (active, unexpired, within limit)
  that takes no branch/merchant/user row locks. Fall back to the existing
  locked path for expiry, renewal, and exhaustion.
- A real-Postgres regression test, seen failing before the fix. No migration
  (query-only change).

Out of scope: request_logs batching redesign, queue/timeout tuning, deploys.

## Closeout update — 2026-09-25

fix reached production. The operator's later distinct-slip ladders, checked
against CloudWatch, recorded zero 5xx at 600–1,200 requests/min. At the
1,200/min shared bank budget, all requests through the 1,100/min step received
bank answers (HTTP 200 or KBank rejection 422); the 1,200/min step produced
77 budget 429 responses. These were single-minute steps, so this closeout
does not claim 1,100 successful HTTP 200 responses or sustained five-minute
capacity. The tracked shared token remains under the operator's explicit
temporary testing decision; rotation/revocation is separate follow-up work.
